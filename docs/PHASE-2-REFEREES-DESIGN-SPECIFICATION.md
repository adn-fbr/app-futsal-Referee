## 1. Evidence Baseline

### Verified facts

- `/referees` and `/referees/:id` are registered in [src/App.tsx](../src/App.tsx) behind `ProtectedRoute requireAdmin requireProfileComplete`.
- `requireAdmin` resolves to `admin_provinsi` or `admin_kab_kota` in [src/contexts/AuthContext.tsx](../src/contexts/AuthContext.tsx).
- The list is implemented by [src/pages/Referees.tsx](../src/pages/Referees.tsx); the detail route is [src/pages/RefereeDetail.tsx](../src/pages/RefereeDetail.tsx).
- The data and mutation surface is [src/hooks/useReferees.ts](../src/hooks/useReferees.ts).
- The current list uses `get_referees`, `count_referees`, client-side expiry filtering, client-side statistics, cards, search, filters, pagination, and page-only CSV export.
- The current detail query uses `profiles.select("*")`; sensitive document URLs are generated by [src/hooks/useSignedUrl.ts](../src/hooks/useSignedUrl.ts).
- `audit_logs`, `get_audit_logs`, and shared audit writers exist in [src/lib/authAudit.ts](../src/lib/authAudit.ts) and [src/hooks/useAuditLogs.ts](../src/hooks/useAuditLogs.ts).
- The generic `/users` route renders [src/pages/UserManagement.tsx](../src/pages/UserManagement.tsx), is restricted to `admin_provinsi`, and creates users for arbitrary roles. It is not proven to be an official referee-onboarding flow.
- Current tokens are defined in [src/index.css](../src/index.css) and [tailwind.config.ts](../tailwind.config.ts): HSL dark-green institutional palette, semantic success/warning/info/destructive colors, spacing from Tailwind, and `Inter` body typography.
- Current production SQL grants `get_referees` and `count_referees` to both `anon` and `authenticated`; the current production function body contains the legacy authenticated-or-active-public fallback.
- The generated Supabase type for `get_referees` omits `kabupaten_kota_name`; a historical migration contains a region-aware return field. This is a contract drift finding, not a UI decision.

### Unknowns that remain open

- Effective live Storage policy and intended document capability per role.
- Whether `/users` is intentionally reused for referee creation.
- Approved export scope.
- Authoritative account/license status vocabulary and exact expiry boundary semantics.
- Whether referee profile/document/export events are required in the existing audit system.
- Effective live function grants and authorization behavior in the Production project.
- Whether `admin_kab_kota` region scope is enforced for every list/detail/mutation path.

## 2. Finding Categories

### Category A - UI/UX Safe

These can be implemented without changing backend contracts, provided they preserve existing behavior:

- Page header and information hierarchy.
- Existing-token spacing, typography, grouping, and responsive presentation.
- Accessible names, labels, focus treatment, and semantic pagination improvements.
- Loading skeletons that preserve query behavior.
- Distinct empty, filtered-empty, error, retry, and permission presentations.
- Explicit page-only export wording without changing export scope.
- Filter sheet usability, active-filter summary, clear actions, and query-preserving interaction.
- Account-state presentation using the existing `is_active` boolean.
- Confirmation dialog for status changes, only stating verified consequences.
- Desktop table/mobile card presentation using fields already available from the approved client contract.

### Category B - Contract Dependent

Do not implement until the owner decision is recorded:

- `kabupaten_kota_name` in list data (`DATA-001`).
- Account versus license status vocabulary and expiry semantics.
- Four-metric summary, especially accurate expiring count.
- Referee creation CTA and `/users` relationship.
- Export scope and approved export fields.
- Whether license/KTP controls are visible to Kab/Kota admins.
- Detail projection and any new referee identifier field.
- Field validation requirements and editable-field rules.

### Category C - Security/Backend

Do not mark these fixed through frontend changes:

- Signed URL authorization and Storage policy (`SEC-001`).
- `profiles.select("*")` minimization (`SEC-002`).
- `get_referees`/`count_referees` `SECURITY DEFINER` behavior and public grants (`SEC-003`).
- Cross-region access and IDOR resistance.
- RLS and mutation authorization.
- Audit event persistence and server-side audit guarantees.
- Server-side expiry filters and aggregates (`PERF-001`, `PERF-002`).
- CSV injection hardening if export serialization is changed (`SEC-004`).

## 3. Contract Question Resolution

### Q1 - Sensitive documents

- **Question:** Who may view and download license documents and KTP documents?
- **Current evidence:** Preview/download controls are visible only for `isAdminProvinsi()`, but `useSignedUrl` is called for every loaded detail viewer and images render whenever a signed URL exists.
- **Known:** The observed UI intent is province-admin-only for preview/download. Storage authorization is not proven. Kab/Kota route access to detail exists.
- **Unknown:** Whether Kab/Kota admins are allowed to view, whether view and download differ, and whether Storage/RLS enforce the same boundary.
- **Impact:** Potential sensitive-document disclosure; P0 security blocker.
- **Owner decision:** Product/security/data owner must define view and download capability separately for license and KTP.
- **Safe behavior until decision:** Do not broaden access. Do not add document controls. Do not change Storage authorization. Treat province-admin-only as the conservative UI intent, while leaving backend verification open.
- **State:** `OPEN`.

### Q2 - Add referee

- **Question:** Is `/users` the official referee onboarding workflow?
- **Current evidence:** The plus action navigates to `/users`. `/users` is generic User Management, restricted to `admin_provinsi`, and creates users with selectable roles including `wasit`.
- **Known:** `/users` is a generic user-management route; no referee-specific creation contract is established from `/referees`.
- **Unknown:** Whether product intentionally uses generic user creation to onboard referees, and whether profile completion/region rules are sufficient for that workflow.
- **Impact:** Misleading primary action and possible role/onboarding regression.
- **Owner decision:** Confirm A/B/C/D: official referee onboarding, generic user management, temporary route, or incorrect route.
- **Safe behavior until decision:** Do not create a new workflow and do not silently reroute. Remove the prominent FAB or relabel it accurately only in an approved UI change. Existing route behavior remains unchanged pending approval.
- **State:** `OPEN`.

### Q3 - Export scope

- **Question:** Should export cover the current page or all filtered results?
- **Current evidence:** `exportRefereesToCSV` receives the loaded `referees` array; with page size 50, current behavior is page-only.
- **Known:** Current behavior is page-only.
- **Unknown:** Whether business users expect all filtered rows and whether a bounded backend export exists.
- **Impact:** User expectation and possible data overexposure.
- **Owner decision:** Approve page-only or all-filtered export and approved fields.
- **Safe behavior until decision:** Keep page-only behavior and label it `Export halaman ini`; do not imply all-filtered export and do not add sensitive fields.
- **State:** `OPEN`.

### Q4 - Status and expiry

- **Question:** What is the authoritative account/status and license/expiry model?
- **Current evidence:** Current UI uses `is_active` for account state and a date-based warning/filter for license expiry. Migrations show `license_level` constrained to `level_1`, `level_2`, `level_3`; other `status` enums belong to different domains.
- **Known:** `is_active` is the current referee account signal. `license_expiry` is a date. The list currently supports `active`, `inactive`, and within-30-days filtering.
- **Unknown:** Approved labels, whether expired licenses block assignment in this area, inclusive date boundary, timezone, and whether `pending`, `suspended`, or `revoked` apply to referees here.
- **Impact:** Incorrect operational decisions if new status labels are invented.
- **Owner decision:** Approve separate account and license vocabulary plus expiry semantics.
- **Safe behavior until decision:** Keep `Aktif`/`Non-Aktif` for account state and existing date warning/filter behavior. Do not introduce new database statuses.
- **State:** `OPEN`.

### Q5 - Audit events

- **Question:** Must referee edits, status changes, document access, and exports be audited?
- **Current evidence:** `audit_logs` storage, `get_audit_logs`, `AuditLogs` UI, and `writeAuditLog` exist. Referee mutations/export/document access do not currently write through this mechanism.
- **Known:** An existing audit infrastructure can be reused; no referee-specific action contract is verified.
- **Unknown:** Required action names, actor/entity metadata, document access policy, export logging requirements, and whether writes must be server-side.
- **Impact:** Compliance/auditability and possible creation of an inconsistent parallel system.
- **Owner decision:** Security/product owner defines required events and authoritative writer.
- **Safe behavior until decision:** Do not create a parallel audit system. Document the requirement and preserve current behavior.
- **State:** `OPEN`.

### Q6 - `get_referees` authorization

- **Question:** What are the effective grants and caller/region rules for `get_referees` and `count_referees`?
- **Current evidence:** Checked-in Production SQL grants both functions to `anon` and `authenticated`; the function body uses `auth.role() = 'authenticated' OR p.is_active = true`. Existing security documents classify the public fallback as unresolved. Historical migrations and current schema disagree on return columns/signatures.
- **Known:** The checked-in artifact is not proof of effective live Production state; route protection does not protect direct RPC calls.
- **Unknown:** Live grants, live function body, RLS interaction, region scoping, and whether the current target has been remediated.
- **Impact:** Direct data exposure, cross-region access, or IDOR; P0 security blocker.
- **Owner decision:** Backend/security owner must verify live behavior and freeze an authenticated, region-aware contract.
- **Safe behavior until decision:** Do not modify RPCs, grants, RLS, or UI claims. Keep `SECURITY FINDING OPEN`.
- **State:** `OPEN`.

## 5. Final Design Specification

### Page header

- Title: `Wasit`.
- Supporting text: `Kelola data dan status wasit AFP Sulsel.`
- Primary CTA: pending Q2; no misleading plus action in the approved interim design.
- Existing `AppLayout` and project typography/tokens remain the base.

### Operational summary

- Four slots are reserved: `Total`, `Aktif`, `Akan berakhir`, `Nonaktif`.
- `Akan berakhir` is rendered only after an accurate aggregate contract is approved; otherwise omit it or show an explicitly unavailable state, never a fake zero.
- Summary loading uses skeletons; errors show `Data ringkasan tidak dapat dimuat` with retry where the query supports it.
- Account state remains boolean-backed `Aktif`/`Nonaktif` until Q4 is resolved.

### Search

```text
[ Cari nama, lisensi, atau asal AFK...                         Clear ]
```

- Accessible label: `Cari wasit`.
- Approved search fields remain name, license, and AFK origin unless contract owner approves more.
- Do not search phone, email, identity numbers, or documents by default.
- Preserve the query across pagination and filter changes.
- Clearly distinguish `Hasil pencarian untuk "..."` from `Belum ada data wasit`.
- Add debounce only if measured/request volume supports it; this is a UI performance decision, not a contract change.

### Filters

Desktop exposes compact controls for Status, Wilayah, Lisensi, and Masa berlaku. Mobile uses a labeled `Filter` trigger with active count and a focus-managed sheet.

Sheet contract:

```text
Filters
  Status: Semua / Aktif / Nonaktif
  Wilayah: Semua Kab/Kota / approved values
  Lisensi: Semua / level_1 / level_2 / level_3 labels
  Masa berlaku: current approved expiry filter only
  Reset
  Terapkan
```

Selections remain temporary until `Terapkan`; `Reset` clears both temporary and applied filters. Active filters are always visible outside the sheet.

### Desktop data presentation

Use an existing shadcn table pattern if introduced during implementation:

| Column | Content | Contract status |
|---|---|---|
| Wasit | Avatar, name, approved identifier if available | Safe except identifier decision |
| Wilayah | Kab/Kota | Contract dependent (`DATA-001`) |
| Lisensi | Existing license label | Existing values only |
| Status akun | Aktif/Non-Aktif | Existing boolean |
| Masa berlaku | Date/approved expiry label | Existing date, semantics open |
| Actions | Detail/edit/status only when authorized | Capability dependent |

Do not add email, phone, KTP, license image, internal metadata, or unapproved identifier columns.

### Mobile data presentation

Use a card/list rather than a compressed table:

```text
Avatar  Nama Wasit                         Actions
        approved secondary identity
        Lisensi level
        Wilayah, if contract available
        [Account status] [License attention, if approved]
```

Long names wrap; actions have an accessible name and comfortable touch target. No destructive action is placed in a dominant floating button.

### Status system

- Account: `Aktif` / `Non-Aktif`, backed by `is_active`.
- License: current date/expiry language only until Q4 approves a vocabulary.
- Possible presentation after approval: `Valid`, `Akan berakhir`, `Expired`, but these are labels, not new database values.
- Every status includes text; color is supplemental. Use existing semantic tokens: success, warning, destructive, muted.

### Detail and edit

- Keep `/referees/:id`.
- Header includes back navigation, identity, account state, approved license data, and authorized actions.
- Edit form uses explicit labels, required indicators only where contractually required, field-level errors, pending save state, cancel behavior, and unsaved-change handling only if the local dialog pattern supports it.
- Save feedback must reflect actual mutation completion; never show a preemptive success state.
- Sensitive documents remain capability-gated and unresolved until Q1/Q6 backend verification.

### Destructive actions

For activate/deactivate, use a confirmation dialog only when the consequence text is verified. Example safe wording:

```text
Nonaktifkan Wasit?
Status akun akan berubah menjadi Non-Aktif.

Batalkan     Nonaktifkan
```

Do not claim event-assignment consequences unless confirmed by business logic.

### State copy

- Empty database: `Belum ada data wasit.`
- Search/filter empty: `Wasit tidak ditemukan. Coba ubah kata kunci atau filter.`
- Query error: `Data wasit tidak dapat dimuat.` + `Coba lagi`.
- Permission: `Anda tidak memiliki akses ke data wasit.`
- Result range with rows: `Menampilkan 1–50 dari 128 wasit`.
- Zero rows: `0 wasit` or the empty-state copy; never `1-0 dari 0 wasit`.
- Export interim wording: `Export halaman ini`; completion must report the actual loaded count.

## 10. Responsive Specification

### Desktop

- Page header and four summary slots in a stable grid.
- Search/filter controls in one scan line where space allows.
- Table for comparison with identity first and actions last.
- No horizontal overflow at laptop width.
- Secondary fields remain visually subordinate.

### Tablet

- Summary can wrap to two rows.
- Filter controls may collapse into a single filter trigger.
- Table may reduce columns to identity, license, account status, and actions.
- Long names, chips, and pagination must wrap without changing control height unexpectedly.

### Mobile

- First viewport: title, purpose, result context, search, filter trigger, and first card.
- Card/list presentation, never a forced wide table.
- Search is full width with clear action.
- Filters use a bottom sheet with focus management and explicit Apply/Reset.
- Actions use an accessible menu; no destructive FAB.
- Preserve safe-area padding above mobile navigation.
- Verify 320px-class widths, zoom/reflow, long names, active chips, dialogs, and pagination.

## 11. Accessibility Specification

Target: WCAG 2.2 AA.

- Search has a visible or visually-hidden label and a clear-button accessible name.
- Filter trigger announces current active count and expanded state.
- Export button announces `Export halaman ini`.
- Any action menu trigger has a row-specific accessible name.
- Dialogs trap focus, return focus to the trigger, and expose title/description.
- Sheets have correct focus entry/exit and do not hide active selections.
- Pagination exposes current page with `aria-current`, disabled previous/next state, and keyboard activation.
- Table has caption/headers; mobile cards use list semantics where appropriate.
- Avatars use meaningful alt text or are explicitly decorative.
- Account/license state uses text plus semantic icon/color, never color alone.
- Query, filter, mutation, and save outcomes use status/live-region announcements where the existing toast system does not provide sufficient assistive feedback.
- Respect reduced motion; retain focus visibility and contrast from existing semantic tokens.
- Do not add visual-only status or controls that are absent from the accessible name.
