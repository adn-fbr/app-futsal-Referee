# Phase 1.8D Synthetic Fixture Specification

## Status

Design only. No fixtures were created.

## Fixture graph

```text
PROVINSI_A -> KAB/KOTA_A -> USER_A -> RESOURCE_A
PROVINSI_B -> KAB/KOTA_B -> USER_B -> RESOURCE_B
```

Use the actual runtime relationships, not parallel test tables.

## Identity and roles

Create synthetic Auth users only in the test project:

- `USER_A`: ordinary `wasit` for region A.
- `USER_B`: ordinary `wasit` for region B.
- `ADMIN_PROVINSI`: platform role.
- `ADMIN_KAB_KOTA_A`: region A admin.
- `PANITIA_A`: region A operator.
- `EVALUATOR_A`: region A evaluator.

Role rows belong in `user_roles`; regional scope belongs in the actual `profiles.kabupaten_kota_id` and regional hierarchy.

## Resources

Use real tables where present: `events`, `event_assignments`, `event_approvals`, `honors`, `evaluations`, `evaluation_scores`, `referee_cards`, `notifications`, and audit/log records generated by tested operations. At minimum create one region-owned resource A and one resource B with explicit region links.

## Naming and determinism

Prefix non-production records with `SECURITY_TEST_`. Use fixed known UUIDs only where the schema permits and the fixture runner owns them; otherwise capture generated IDs in CI outputs without logging PII or secrets.

## Safety

Fixture setup must require `TEST_ENVIRONMENT=non-production`, reject the production project ref/URL, use service role only in protected setup, and never copy production rows.
